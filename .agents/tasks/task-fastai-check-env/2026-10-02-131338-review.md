# `fastai_check_env` CLI — one-step environment validator

Adds a hand-authored `fastai/check_env.py` module and a `fastai_check_env` console script that validates the Python version, the GPU/CUDA stack exposed through PyTorch, the presence/versions of 14 key dependencies, and installed versions against the ranges declared in `settings.ini`. Every check reports instead of raising, so the tool produces a diagnosis precisely in the broken environments it exists to diagnose. Exit code is `0` unless a *hard* incompatibility is found (Python below `min_python`, or an installed dependency violating its `settings.ini` range). The implementation follows the fork's established "added feature" pattern — standalone module under `fastai/` plus a pytest file under `tests/`, no paired notebook, no `_modidx.py` entry — so the nbdev-sync CI gate stays clean.

Watch for: the module hard-codes the constraint set (`_CONSTRAINED_REQUIREMENTS`) rather than reading `settings.ini`, and it omits two constraints that `settings.ini` actually declares — `spacy<4` and `packaging` are never version-validated (possible). A drift test covers only `torch`, so the other hard-coded ranges can silently diverge from `settings.ini` (confirmed). Both are design-boundary observations, not defects in what is implemented.

**Verdict**: APPROVED

## High-level view

The fail-open posture is the backbone: `check_torch`, `check_cuda`, and `check_dependencies` return `WARNING`/`INFO` for anything missing or broken, and only `check_python` and `check_version_constraints` can emit `ERROR`. `check_env` derives `compatible` purely from the `ERROR` count and `main` maps that to the exit code, so the docstring's "hard incompatibility" definition, the per-check severities, and the exit-code logic all agree.

CUDA inspection wraps each torch surface (`version.cuda`, `is_available`, `device_count`, `get_device_name`, `cudnn`) in its own guard, so a driver that throws from `is_available()` or a GPU whose name can't be read degrades to a WARNING or a placeholder string rather than crashing.

`_specifier_contains` returns a three-valued result — `True`/`False`/`None` — where `None` (packaging missing or unparseable version) maps to WARNING, never ERROR, so an environment that merely can't be verified is not failed.

The constraint source is the design boundary to see clearly: `_CONSTRAINED_REQUIREMENTS`/`_MIN_PYTHON` are a hand-maintained copy of `settings.ini` (justified by the module needing to work as a wheel with no `settings.ini` on disk). That copy omits `settings.ini`'s `spacy<4` and `packaging` constraints, and the drift guard only pins `torch`.

The tests inject a fake `torch` and monkeypatch `_dist_version`, exercise the real code paths, and would fail if the implementation were reverted. The coverage gaps are in the constraint-drift direction, not the behavioral direction.

### Fail-open severity model and the exit-code contract

The two ERROR producers are exactly the two conditions the docstring names as "hard": `check_python` below `min_python`, and `check_version_constraints` when an *installed* dependency's version is outside its range. A not-installed constrained dependency is `INFO` and an unverifiable one is `WARNING` — neither fails the run, so a wrapper that keys off the exit code is not tripped by a merely-missing dependency.

`check_python` compares `sys.version_info[:3]` truncated to `len(min_python)` against the tuple, so `(3,12)` on 3.11 fails and `(3,9)` passes — the `test_old_python_flagged_error` / `test_exactly_min_python_passes` pair exercises both directions against the live interpreter.

### Version-constraint semantics

```python
return (parsed in spec) or spec.contains(parsed, prereleases=True), None
```

The two-arm check is deliberate: `parsed in spec` uses packaging's default prerelease exclusion, and the `or spec.contains(..., prereleases=True)` arm then accepts an in-range prerelease (e.g. `2.0.0rc1` against `>=1.10,<2.6`). A prerelease *below* the lower bound still returns `False`, and the exclusive upper bound (`2.6` against `<2.6`) returns `False` — both confirmed by running the real function. The three-valued contract (`None` for missing-packaging or unparseable version) is what keeps an unverifiable environment at WARNING; `test_unverifiable_without_packaging_is_warning` and `test_missing_dependency_is_info_not_error` lock that in.

### Constraint source: drift risk and the omitted constraints

`TestSettingsIniConsistency` pins `min_python`, the `torch` range, and the console-script registration, but not the other five constrained ranges (fastcore, torchvision, fastprogress, fastdownload, pillow) — and the constraint set itself is a subset of `settings.ini requirements`, missing `spacy<4` and `packaging`. Net effect: an installed `spacy>=4` violates `settings.ini` but would be reported only as a presence `OK`, not a hard ERROR. A `spec`-substring assertion per constrained entry would close the drift gap; a comment or an added `spacy`/`packaging` entry would resolve the subset question.

### Tests exercise real paths and are revert-sensitive

The suite monkeypatches `_dist_version`/`_specifier_contains` only to pin inputs, leaving the function-under-test real. `test_cuda_available_reports_devices` asserts the exact `devices`, `device_count`, and `cudnn_version` the code must assemble from the fake torch, so removing the per-device `get_device_name` loop would fail it; `test_main_returns_nonzero_on_hard_incompatibility` drives the ERROR→exit-code path through `main`. The `no_torch` fixture sets `sys.modules['torch']=None` so `import torch` raises `ImportError` — the standard way to simulate absence.

### Style/contract match with the gradient_noise reference

Matches the reference pattern: module-level docstring with a usage block, `__all__`, terse one-line function docstrings in the fastai house style, no notebook, no `_modidx.py` entry (confirmed absent for both modules), and a sibling `tests/test_*.py`. One intentional divergence: `gradient_noise.py` imports `torch` at module top (it is a training callback and torch is a hard dep there), whereas `check_env.py` must import torch lazily inside each check — correct for a tool whose job is to run when torch is missing.
